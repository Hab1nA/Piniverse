# 07 · 上下文与信息流

> 状态：草案 Draft v0.1 · 2026-08-29
> 上游：[03 消息协议](03-message-protocol.md) · [04 控制关系](04-control-relations.md) ｜ 下游：[11 实现路线](11-implementation.md)

多 Agent 系统最常见的死法不是协议错误，而是**上下文淹死**：结果、转录、日志层层回流，每个会话都被别人的工作撑爆。本文件定义 Piniverse 的信息流纪律。

## 本章要点

- 三条信息通路各有分工：**消息**传决策与状态，**工件**（共享文件系统）传大数据，**注册表**传身份与事实。
- 核心纪律是"**传指针，不传全文**"：消息只携带路径 + 摘要 + 校验和。
- 逐跳摘要：每个 worker 交付时给出 ≤300 字 summary，master 汇总子成果时基于 summary 而非重读全文。
- 契约状态用 `pi.appendEntry` 持久化（不进上下文、跨 compaction 存活），必要时以**状态卡**重新注入。

---

## 1. 三条信息通路

| 通路 | 适合承载 | 不适合承载 | 规范 |
|------|---------|-----------|------|
| **消息**（[03](03-message-protocol.md)） | 决策、请求、状态、进度、指令、小结论（KB 级） | 大文件内容、长转录、批量数据 | body ≤ 8 KB；一切大数据给指针 |
| **工件**（共享工作区文件） | 代码、文档、数据集、报告、日志——一切交付物与中间产物 | 纯状态类信息（那属于注册表/消息） | 放在 spec.deliverable 约定的位置；消息携带 `{path, digest?}` |
| **注册表**（[05](05-registry-lifecycle.md)） | 身份、能力、状态、信誉、契约台账、预算余量 | 任何任务语义内容 | 只存事实与计数；语义判断留给读它的人 |

判据一句话：**换一个模型还能复原的信息走工件，需要对方"知道"的走消息，需要全网"看见"的走注册表。**

## 2. 传指针，不传全文

- **前提假设（MVP）**：网络中所有对等体共享同一工作区文件系统（单机、同目录或嵌套子目录，[02 §3](02-architecture.md#3-进程与文件布局)）。因此"指针"就是相对工作区根的路径。
- **指针格式**：`{path, digest?}`——digest 为内容 sha256 前 16 位，用于接收方校验"我读到的就是你交付的"。可选但强烈建议在 result 中提供。
- **绝对路径的例外**：跨工作区引用（ policy 允许时）用绝对路径，并在 `refs` 中标注来源工作区；跨机场景是开放问题（Q6）。
- **消息里贴内容片段的纪律**：允许贴**结论性短文**（≤300 字）；贴代码必须给路径+行号区间而不是全文。模型很爱贴全文——这是 pv-ext 无法机械校验的少数纪律之一，靠指南 + review 反馈训练（诚实承认，见 §7）。

## 3. 逐跳摘要与验收

```mermaid
flowchart LR
    subgraph 向上流动（收敛）
        W["worker: result<br/>summary ≤300字 + 工件指针"] --> M["master: 汇总<br/>基于子 summary 与抽查"] --> R["根: 最终交付"]
    end
    subgraph 向下流动（展开）
        R -. "spec: 目标+交付物+验收标准" .-> M -.-> W
    end
```

- **spec 锁定期望**：request 的 goal/deliverable/acceptance 让 worker 不必知道"上游的全局背景"也能对准靶子。委托的艺术在于 spec 写得让 worker **不需要**母任务的全文语境——写不好 spec 的会话不适合当 master，这是协议指南明说的。
- **summary 是汇报货币**：result.summary（≤300 字）与 report.notes 是上游了解下游的唯一常规窗口。master 向上交付时，其 result.summary 基于各子契约的 summary 汇总 + 必要的抽查，而不是把子报告全文粘贴上来——**逐跳压缩**保证上下文消耗随网络深度只是线性累加，不会指数放大。
- **验收标准使 review 便宜**：reviewer 检查的是"acceptance 逐条是否满足"，通常只需读工件的关键部分。宁可 spec 里写五条硬标准，不要 review 时凭感觉——指南要求 acceptance 可检验（"npm test 全绿"✓，"代码质量好"✗）。

## 4. 进入 Pi 上下文

一个对等会话的上下文由四类来源构成，各有预算纪律：

| 来源 | 进入方式 | 预算纪律 |
|------|---------|---------|
| 收到的消息 | 投递注入（`customType:"pv-message"`） | 每 turn ≤10 条、>32 KB 自动合并 report（[03 §7](03-message-protocol.md#7-与-pi-注入机制的对齐)） |
| 自身工作 | 正常 Pi turn（工具结果、文件读写） | Pi 自身的 compaction 机制负责 |
| 状态卡 | `before_agent_start` / compaction 后注入 | 固定 ≤1 KB，见下 |
| 协议指南 | system prompt（`systemPromptAppend`） | 固定 ~1.5 KB，一次性 |

**状态卡**是 pv-ext 为自己会话生成的极简台账，形如：

```text
[PV 状态卡] 我=pv-beta(b81de47) busy
  欠 pv-alpha: t-9f3e21ab (active, 62%, 预算余 45k tokens, deadline 18:00)
  收 pv-gamma: t-4c1d… (reviewing, 待我验收)
  待办: 回复 alpha 的 steer(14:32)
```

- 生成时机：`before_agent_start` 每次刷新注入；长度超过 1 KB 时自动裁剪（只保留 active 契约与最老待办）。
- 数据源：`pi.appendEntry` 的簿记（§5），不依赖对话记忆——**模型忘了没关系，扩展记得**。

## 5. 与 compaction 协同

Pi 的自动 compaction 会摘要并压缩对话历史，这带来一个契约系统的特殊要求：**流程状态必须比对话记忆活得更久**。分工：

- **`pi.appendEntry`（持久簿记）**：契约簿记、信箱游标、msg_id 去重环、状态卡原始数据。entry 不进 LLM 上下文、不被 compaction 压缩、随会话文件持久化——这是**流程真相**的所在地。
- **注册表契约存储**：跨会话的契约台账（物化视图）。本会话视角与其一致性由重放保证（[04 §5](04-control-relations.md#5-关系即协议状态由消息推导)）。
- **对话上下文**：允许被压缩。compaction 后的第一个 turn，pv-ext 注入状态卡 + 可选的 `check_inbox` 提示；丢失对话细节是可接受的——工件在文件里，事实在日志里，账在 entry 里。

**验收要点（M2）**：模拟一次 compaction 后，会话仍能正确完成"验收一份交付、辞任一份契约"。任何需要"记得第 3 天说过什么"才能继续的流程都是设计错误——这类信息本该在 spec、工件或消息里。

## 6. 隐私与最小披露

- **对等体之间看不到彼此的对话内容**。发现工具暴露档案/能力/状态/信誉（[05 §4](05-registry-lifecycle.md#4-发现)），仅此而已。一方想知道另一方的工作进展，唯一通道是它发出的 report（以及工件文件）。
- 这不仅是隐私，更是**上下文卫生**：如果对等体可以互相翻转录，跨会话的上下文隔离就形同虚设，网络规模越大每个节点越肿。信息必须经过**消息化或工件化**的有意压缩才能跨越边界。
- **对操作员无隐私**：`pv-human` 与 hub 可以查看全部消息与审计日志（治理需要，[08 §5](08-safety-governance.md#5-审计日志)）。这是刻意的：对等体之间的"保密"是防上下文爆炸的工程手段，不是对抗人类的机制。
- **工件的最小授权**：契约可以约束 worker 的文件操作范围（[08 §3](08-safety-governance.md#3-策略执行点) 的按契约限权），但 MVP 的文件系统是共享的，"逻辑隔离"靠 spec.constraints 与钩子拦截，物理隔离靠容器化（[08 §7](08-safety-governance.md#7-与-pi-容器化的对接)）。

## 7. 推荐 / 备选 / 开放问题

**推荐**：三通路分工；8 KB 消息上限 + 指针纪律；≤300 字逐跳摘要；状态卡 ≤1 KB；appendEntry 作为流程真相。

**备选**：(a) 对等体共享一个"黑板"文件（经典黑板架构）——写入冲突与上下文污染风险高，且把协调降格为文件竞争，否决；(b) 消息支持二进制附件（如 base64）——破坏"一切皆文本"与可 diff 性，一律用文件指针替代；(c) 自动把收到的 report 全文存进会话记忆——上下文膨胀，否决；report 已在审计日志，需要时 `check_inbox` 重读。

**开放问题**：跨工作区/跨机的指针语义（Q6）；摘要质量的自动化检查（summary 与工件不符的检测，Q7）；"贴全文"纪律的机械约束可行性（如 body 中连续 >N 行非路径文本的启发式警告，Q7）；状态卡是否应暴露更多上下文（如最近 3 条消息的标题）以减少 check_inbox 频率（Q14）。

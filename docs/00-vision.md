# 00 · 愿景与核心思想

> 状态：草案 Draft v0.1 · 2026-08-29
> 上游：无 ｜ 下游：[01 概念](01-concepts.md) · 全部设计文档

## 本章要点

- Piniverse 的目标：基于 [Pi](https://github.com/earendil-works/pi) 构建一个**平级会话网络**——所有 agent 都是能力完全相同的 Pi 会话，主从关系不是制度设定的身份，而是在任务执行中通过消息协商**涌现**出来的临时契约。
- 系统只引入**一个新原语：跨会话消息**。委托、汇报、转向、取消、升级，全部是消息。
- 权力来自契约而不是出身：任何会话都可以委托，任何会话都可以受托、拒绝、还价、辞任；控制是相互的、有界的、可解除的、全程留痕的。

---

## 1. 问题：机构式层级的三个代价

当前主流多 Agent 系统（Claude Code / ZCode 的 Task 子代理、Pi 官方的 subagent 扩展示例、CrewAI 的 hierarchical 模式）都采用**机构式层级**：父代理在创建子代理的瞬间被制度性地授予权力，子代理被制度性地定义为"下级"。这个模型简单有效，但有三类结构性代价：

1. **深度有天花板。** 子代理通常不能再委托（depth=1），或者层级被框架固定。"委托"是父代理的特权，而不是所有会话的同等能力。复杂的真实任务天然具有递归结构，天花板迫使父代理上下文膨胀、或迫使人类手动拆分。
2. **权力不可见、不可协商。** 子代理没有拒绝权、没有还价权、没有对父代理的反馈通道——它甚至不能抱怨。控制关系是单向的、建立即生效的、无法审查的。而在人类组织中，恰恰是"受托方可以说不、可以要求澄清、可以中途报告风险"这些反向机制保证了质量。
3. **组织形态与任务形态脱节。** 无论任务是线性流水线、星型分发还是菱形评审，机构式层级的拓扑在任务开始前就被"谁创建了谁"写死，而不是随任务生长。

Piniverse 的核心主张：**层级本身是有价值的，但层级应该是任务的属性，而不是代理的身份。** 主从关系应当像人类世界的承包合同——由双边同意建立、约定权利义务、随时可解除、全程留痕——而不是像科层制里的上下级任命。

## 2. 愿景：一个由对等会话组成的宇宙

Piniverse（Pi + universe）是一片由 Pi 会话组成的对等空间。三条命题定义了它：

### 命题一：所有会话生而平等（Peer Equality）

网络中的每个节点都是一个**完整的、能力相同的 Pi 会话**：同一套内置工具、同一个 system prompt、同样的扩展配置。没有任何会话携带"你是子代理"之类的身份设定，没有任何会话被剥夺或增加工具。存在过的所有差异——某人擅长什么、当前忙不忙、信誉如何——都是它自己通过注册表**声明**和**积累**的，不是框架授予的。

> 推论：今天被委托的会话，下一分钟可以自己委托别人。深度没有制度天花板，只有策略护栏（见 [06 网络动力学](06-network-dynamics.md)）。

### 命题二：消息是唯一的协调原语（Message as the only Primitive）

会话之间没有任何直接控制通道——没有"spawn 并获得句柄"、没有共享内存、没有函数调用。一个会话对另一个会话能做的**唯一事情，就是把一条结构化消息投进它的信箱**。想委托任务？发 `request`。想中途改需求？发 `steer`。想拒绝？发 `decline`。所有协调行为在协议层面同构，因此也同等可记录、可审计、可重放。

> 推论：基础设施（注册表、信箱、枢纽）只做无决策的搬运与记账——它验证格式、投递、记录、按策略拦截，但**从不决定**谁该收到什么任务。决策永远属于某个会话的 LLM，或属于人类操作员。

### 命题三：主从关系是涌现的契约（Master/Sub as Emergent Contract）

"主代理/子代理"不是任何会话的属性，而是**两个对等体之间随任务诞生、随任务消亡的任务契约（Task Contract）**：

- A 向 B 发出 `request`（附任务规格、交付标准、预算），B 可以 `accept`、`decline` 或 `counter`（还价）。**双边同意才建立关系。**
- 契约生效期间，A 获得对 B 的**有界权利**：转向（steer）、查询进度、取消、验收；B 承担**有界义务**：按里程碑汇报、守预算、按规格交付。**同时 B 也保留权利**：拒绝超范围的 steer、无力时 `resign` 辞任、以及在自身契约范围内**继续转委托**——网络由此生长。
- 任务完成、验收通过，契约终止，关系随之消失。任何时刻，全部活跃契约的集合构成一张动态 DAG——这就是那个自发组织的 Agent 网络。

> 推论：A→B→C→D 的委托链上，每一跳都是一份独立的双边契约。D 的"主"是 C 而不是 A；A 对 C 没有任何直接权力（想干预？只能让 C 去转向 D，或者走 escalation）。权力严格沿契约边传播，网络因此是**可分解审计**的。

## 3. 设计原则

| # | 原则 | 一句话含义 | 主要落点 |
|---|------|-----------|---------|
| P1 | **对等性** Peer Equality | 所有会话同配置、同能力、同 system prompt | [05](05-registry-lifecycle.md) |
| P2 | **消息唯一原语** | 一切协调 = 投递一条信封消息 | [03](03-message-protocol.md) |
| P3 | **关系即协议** Relations as Protocol | 契约状态由消息日志重放推导，日志是唯一事实源 | [04](04-control-relations.md) |
| P4 | **双边同意与可解除** | 委托需 accept 才生效；任一方可单方面终止 | [04](04-control-relations.md) |
| P5 | **机制最小化** Minimal Mechanism | 能靠协议纪律（prompt 指南）解决的用纪律，必须强制的才落在钩子与注册表规则上 | [08](08-safety-governance.md) |
| P6 | **基础设施无决策** | 基础设施验证、投递、记录、按策略拦截；从不选择、从不优化、从不撮合 | [02](02-architecture.md) |
| P7 | **人机同构** Human as Peer | 人类操作员也是网络中的一个节点（`pv-human`），拥有策略赋予的最高权力，而不是框架外的隐形上帝 | [05](05-registry-lifecycle.md) · [08](08-safety-governance.md) |
| P8 | **一切皆文本** Everything is Text | 消息、契约、注册表、审计全部是工作区内的可读文件；可重放、可 diff、可 git | [03](03-message-protocol.md) · [02](02-architecture.md) |

其中 P5 需要特别说明：LLM 的行为纪律（比如"小任务别委托""汇报要精炼"）写进 system prompt 的协议指南，由模型自觉遵守；而**结构性安全**（成环检测、预算不变量、广播限流、按契约限权）落在 `tool_call` 钩子和注册表规则上，由代码强制。区分这两层是本设计能否既灵活又安全的关键。

## 4. 这个设计换来什么

- **无深度天花板的组织能力**：任务递归多深，网络就长多深；任务结束，网络自动解体。
- **拓扑自适应**：星型、链式、树形、菱形评审——拓扑由各会话的局部决策涌现，无需全局编排器。
- **可组合**：任何会话的"参与方式"只有一种（收发消息），因此网络中随时可以加入新会话、退出旧会话，不破坏任何在途契约（孤儿契约有明确的接管规程，见 [06](06-network-dynamics.md#5-故障与接管)）。
- **统一调试体验**：没有两套心智模型。看任何会话，都是看一个普通 Pi 会话；看全局，看契约图与消息日志。
- **权力的可审计性**：谁在什么契约下给谁发过什么指令，全部是追加式日志里的一行。出了问题可以重放归因。

## 5. 代价——诚实清单

对等网络不是免费的：

1. **协商开销**：每次委托都有 request/accept 往返。小任务直接自己做更便宜——因此协议指南会明确"三步以内的任务不要委托"（见 [06 §2](06-network-dynamics.md#2-决策模型会话自己的选择)）。
2. **协议纪律负担**：系统正确性部分依赖 LLM 遵守消息格式与流程。我们用严格的 tool schema + 校验 + 状态机挡住大部分违规，但无法挡住"语义级"违规（汇报内容失实）。缓解：验收环节、信誉展示、事后审计——详见 [08 §8](08-safety-governance.md#8-诚实的局限)。
3. **无全局最优保证**：没有编排器做全局规划，拓扑质量取决于各会话的局部判断。这是刻意的取舍——我们相信局部判断 + 泛滥熔断，优于中心规划的脆弱性（论证见 [06](06-network-dynamics.md)）。
4. **新型故障面**：死锁环、消息风暴、孤儿契约、多主竞争——这些在机构式层级里不存在或不明显的问题，[06](06-network-dynamics.md) 与 [08](08-safety-governance.md) 给出了系统性防护。

## 6. 非目标

- **不做多机分布式**。MVP 明确假设：单机、单工作区（或嵌套子目录）、所有对等体共享同一文件系统。跨机扩展只作为演进方向记录在 [open-questions](open-questions.md)。
- **不做通用多 Agent 框架**。Piniverse 是 Pi 的一个应用层体系（扩展 + 约定 + 可选枢纽进程），不试图成为可挂任意 Agent 的中间件。它深度依赖 Pi 的会话与扩展机制（见 [02 §2](02-architecture.md#2-组件与-pi-的集成面)）。
- **不追求无人监督的全自主**。早期阶段假设操作员在场，escalation 通道必须可用；"人不在场"模式是远期目标。
- **不建立常设组织**。没有永久团队、常设经理、长期绑定。网络随任务聚散；会话间的"记忆"只通过注册表档案与工件文件这类显式载体沉淀。
